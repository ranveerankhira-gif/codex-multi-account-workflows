# 本机多账号 Codex 任务接力契约

## 账号与方向

本机多个 Codex 账号使用独立 `CODEX_HOME` 与界面数据目录，但共享同一 Windows 用户可访问的项目文件。任意两个显式配置且目录不同的账号都可以作为来源或目标。

接力包不得修改来源或目标账号的认证文件、会话数据库、索引或设置。账号名称和账号根目录必须同时绑定，不能只相信一个手写标签。

## 任务检索

用户提供自然语言线索。程序只读取明确指定来源账号的 `session_index.jsonl` 与 `sessions/`，候选必须有索引标题、有效会话和准确项目目录。

`discover` 的排序只是候选缩小工具。选择前必须比较：

1. 用户描述是否对应候选最后一个未完成请求；
2. 末尾消息是完成、进度还是中断状态；
3. 项目现场是否能解释该请求。

相同项目、同标题族或分数接近的候选必须交叉比较。仍无法唯一确定时询问用户；`recover` 必须使用明确任务 ID。

自然语言扫描不得因一个无关的超大、持续变化或损坏会话而整体中止；这类记录写入 `scan_diagnostics` 后继续扫描。若用户以任务 ID 明确选择了该会话，则必须失败关闭，不能跳过正文后继续打包。

## Schema 9 接力包

首次接管和返程统一使用 Schema 9，`package_kind` 分别为 `takeover` 与 `return_handoff`。两类包共同包含：

- 来源与目标账号名称、根目录和任务 ID；
- `RECEIVER_START.md`、`TAKEOVER_METADATA.json` 与 `HANDOFF_CHAIN.json`；
- `PROJECT_SNAPSHOT.md`、`PROJECT_FILE_MANIFEST.json` 与 `GIT_DIFF.patch`；
- `CONVERSATION_INDEX.md`、`FULL_TRANSCRIPT.md`、`READING_MANIFEST.json` 和全部对话分块；
- 内嵌图片附件；
- `REFERENCED_ARTIFACTS.json` 与可取得的显式引用文件；
- 覆盖包内每个文件的 `SHA256SUMS.txt`。

返程包额外包含 `WORK_STATE.md`，并保留收到的接力链后追加一跳。Schema 9 的每一跳都必须记录同一项目根目录；相邻两跳必须满足上一跳 `target_account` 与下一跳 `source_account` 一致。生成返程包前还必须确认上游目标账号、目标账号根目录、项目根目录，以及上游指定时的目标任务 ID，与当前返程来源一致。

Schema 9 不携带可执行接收器。接收方必须使用本机独立安装、已审查的 `recover_main_task.py`；包内哈希不是代码来源或作者身份的证明。旧 Schema 6–8 中的 `RECEIVER_TOOL.py` 只作为普通包文件核验，禁止执行。

## 项目现场

Git 项目记录分支、HEAD、短状态、暂存与未暂存文本 diff，以及未跟踪文件路径、类型、大小和 SHA-256。二进制改动只记录“文件不同”，不把二进制补丁内容塞进接力包。

非 Git 项目递归记录普通文件与内部符号链接的 SHA-256。为避免依赖缓存造成无界扫描，`.git`、`node_modules`、虚拟环境与常见缓存目录会明确列入 `excluded_directories`。清单上限为 20000 个文件、4 GiB；超过上限直接失败，不生成残缺快照。

任何文件或目录链接越出项目根目录默认都必须停止。只有用户明确同意、生成端用 `--allow-external-link` 逐一声明项目内相对目录时，Schema 9 才允许记录该 Junction/符号链接；证明必须包含规范化绝对目标、链接类型、文件数、字节数、排除目录和完整目标目录树哈希。链接目标内部不得再包含目录或文件链接，未声明的外部链接继续失败关闭。接收时按包内路径重新生成同类证明；链接目标或任一目标文件变化就拒绝继续。Schema 9 的非 Git 清单完全一致且没有缺失或不支持的引用文件时可以返回 `ready`。

## 引用文件

只解析用户消息中 `# Files mentioned by the user:` 区段明确列出的绝对本地文件：

- 可检查的 UTF-8 文本和 PNG/JPEG/GIF/WebP 图片复制到 `referenced_artifacts/`，记录原路径、包内路径、大小和 SHA-256；
- 缺失或不支持的路径写入清单，不伪装成已复制；
- 账号根目录中的引用拒绝打包；
- 单文件上限 64 MiB，总量上限 256 MiB，数量上限 100；
- UTF-8 文本检查疑似凭据；图片使用 Windows 本机 OCR，失败或覆盖不全时失败关闭。

存在缺失或无法安全检查的二进制引用文件时，包仍可诚实归档，但 `receive` 不得自动返回 `ready`。

## 完整性验证

`verify` 必须确认：

- 哈希清单与实际文件集合完全相等；
- 元数据、消息数、分块数、附件数与实际文件一致；
- 每个对话分块的消息编号、哈希和正文与完整归档一致；
- 接力链最后一跳与来源、目标、任务和包类型一致；
- Schema 9 的接力链版本、相邻账号、每跳项目根目录和末跳包版本相互一致；
- 项目清单、引用文件清单及其实际文件集合一致；
- 项目清单中的显式外部目录链接记录结构有效、路径唯一且目标树哈希格式正确；
- 图片安全扫描数量与实际图片一致；
- 来源与目标账号不同，根目录不同且不嵌套。

Schema 3 至 8 仅为只读向后兼容。不得把旧包描述成具备 Schema 9 的可执行代码隔离保证。自动返程只接受具备完整接力链的 Schema 7 或更高版本上游包，并统一输出 Schema 9。

## 接收与继续

`receive` 只做只读验证。它必须由本机已审查的 Skill 脚本执行，匹配目标账号名称与根目录，重新证明共享项目现场，并确认引用文件没有缺失或不支持项。返回 `ready` 后，接收方严格按 `read_order` 阅读全部材料，再报告断点并继续。

接力包不会自动写入目标账号旧任务，也不会自动唤醒另一个 Codex。生成端必须报告包的绝对路径与目标账号；目标号在指定任务或新任务中读取它。

## 停止条件

- 多个候选无法可靠区分；
- 会话文件在读取期间变化；
- 项目路径过宽、不存在或与候选不一致；
- 对话或附件疑似包含凭据；
- OCR 失败、引用文件超限或链接越界；
- 项目现场与包内证明不一致；
- 继续需要新的登录、付费、发布、删除或其他未授权外部动作。

用户说“先看看”“暂不实施”时，完成历史、资料和项目现场核对后停止，不修改项目、不运行写入真实数据的测试、不提交 Git。
